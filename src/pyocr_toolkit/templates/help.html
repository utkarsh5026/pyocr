pyocr toolkit guide

pyocr shows you what text you actually get out of a PDF or image, using three different methods, and how far apart they are. Use it to decide whether OCR is good enough for a document set, to pick an LLM for extraction, or just to get clean text out of a difficult file.

Quick start

  1. Upload a file with the Upload button (top right) or by dropping it anywhere on a page. You can upload several at once, or a .zip; those go into a workspace.
  2. The file opens on its Overview page. Each page gets a badge; scan means it has no embedded text, so it needs OCR or an LLM.
  3. Start an extraction: choose an OCR engine or an LLM, a page range (or leave it empty for every page), and click Start extraction. A progress bar follows the job.
  4. Open the Page inspector to see one page next to all of its texts, or Full text to read the whole document from one source.
  5. Use Compare to measure two sources against each other, then export the text you want.

Workspaces and batch uploads

A workspace keeps documents that belong together (a folder of invoices, a zip of scans) under one name.

  • Several files or a .zip. Select or drop more than one file, or any .zip, and a dialog asks where they go: a new workspace, an existing one, or no workspace (just the Library). A single PDF or image skips the dialog and opens right away, as before.
  • Name suggestions. When the files share a name, that comes first: invoices-2024.zip suggests invoices-2024, and report-q1.pdf + report-q2.pdf suggest report. The other ideas are short adjective-scientist names such as festive-albattani; the shuffle button gives new ones. Type anything you like instead; names must be unique (ignoring case) and at most 80 characters.
  • Zips are unpacked on upload. Every PDF or image inside becomes its own document. Unsupported files, zips inside the zip, encrypted entries and files that won't open are skipped, and the dialog lists each one with the reason. __MACOSX folders and hidden files are ignored. Limits: 500 files per zip, each file up to MAX_UPLOAD_MB, and the zip's unpacked total up to 5 × MAX_UPLOAD_MB.
  • Renaming. On the workspace page, click the pencil or double-click the name. Name ideas based on the files are offered there too.
  • Adding later. On a workspace page, Add files or dropping files puts them straight into that workspace.
  • Removing vs deleting. × on a card takes the document out of the workspace but keeps it in the Library; the bin deletes it everywhere. Deleting a workspace asks whether to delete its documents as well.
  • A document can belong to more than one workspace. Its badges in the Library show which ones.

The three text sources, from first principles

1. Native text: the text the file already contains

A PDF page is a list of drawing instructions, for example "use font F at 11 pt, draw glyph 37 at (72, 700)". When a PDF is exported from Word, LaTeX or a browser, each glyph also carries a mapping back to a Unicode character. PyMuPDF follows those instructions and rebuilds words and lines from where the glyphs sit. This is exact, because nothing is guessed, but it only exists for born-digital files. A scanner only records a picture of the page, so a scanned PDF has no glyphs and no native text. A few PDFs also have broken glyph mappings, so native text can be gibberish even though the page looks fine.

2. Tesseract OCR: turning pixels back into characters

For a picture, all we have is pixels. pyocr renders the page at OCR_DPI (300 by default; small text needs enough pixels per character) and gives it to Tesseract, an open-source OCR engine. Tesseract finds lines of text, segments them, and recognises characters with a neural network (LSTM). It also reports a box for every word, which is how search can highlight OCR hits on the page. It is fast, free and private, but it reads shapes rather than meaning. Tables, multi-column layouts, stamps, low-contrast or skewed scans and handwriting are its weak spots.

2b. Other OCR engines

Tesseract is one of several engines, and each engine you run becomes its own source (ocr:<engine>), so you can compare engines against each other or against an LLM. Local engines run on your machine and need an extra install (pip install "pyocr-toolkit[easyocr]"); they download their model the first time: RapidOCR (light, ONNX Runtime), EasyOCR (PyTorch, many languages), PaddleOCR (very accurate on dense and Asian-script pages) and docTR (document-focused, gives blocks/lines/words). Cloud engines send the page image to the service you configured: Google Cloud Vision, Azure AI Document Intelligence, AWS Textract and Mistral OCR. They are usually stronger on handwriting and poor scans, and cost a fraction of a cent per page. Most engines detect whole lines; pyocr orders the lines top to bottom and splits each line box into word boxes by character count, so search highlights land close to the word. Mistral OCR returns Markdown without positions. The Providers page shows which engines are ready and has a Test button for each.

3. LLM transcription: a vision model reading the page

The page is rendered to an image (LLM_DPI, with the longest side capped at LLM_MAX_EDGE_PX) and sent to a multimodal LLM with instructions to act as a transcription engine, not an assistant. Because it reads whole words and sentences in context, it is usually far more accurate than Tesseract on hard pages, and it understands layout. It can also make mistakes OCR never makes: quietly fixing a typo, normalising a date, skipping a repeated header, or occasionally inventing a plausible word for a smudge. Use the diff view to catch these. It also costs money and sends the page image to the provider.

LLM prompts

  • Verbatim (default): plain text, line by line, nothing corrected, tables as cell | cell. Use this to judge OCR, because both outputs then have the same shape.
  • Markdown: keeps structure (headings, lists, GFM tables). Closest to what you would feed a RAG or LLM pipeline.
  • Custom: write your own instructions, for example "extract only the line items as CSV" or "transcribe the handwritten notes only".

Every provider + model + prompt combination is stored separately, so you can run several and compare them. Results are cached: repeating a request costs nothing unless you click re-run.

Adjusting the image before the LLM sees it

A vision model never sees your PDF, only the pixels it is sent. So the pixels are part of the experiment: a grey photocopy, a speckled fax or a faded receipt can read better after cleaning up, and sometimes worse (thresholding can erase a faint decimal point). Adjust on the page inspector (shortcut e) lets you try it and measure it.

  • Filters are presets, each shown as a thumbnail of the current page: Clean scan (grayscale, auto levels, a little sharpening), High contrast, Black & white, Fix faded, Denoise, Bring out detail and Invert (light text on dark). Picking a filter keeps your crop and rotation.
  • Fine-tune: brightness, contrast and sharpness (1 = unchanged), denoise (a median filter: each pixel becomes the median of its 3×3 or 5×5 neighbourhood, which removes isolated specks but keeps edges), black & white, resolution, rotation and crop margins.
  • Black & white turns every pixel pure black or pure white. Automatic uses Otsu's method: it tries every grey level as the cut-off and keeps the one that best separates the image into two groups (ink and paper), meaning the two groups' average brightnesses are as far apart as possible, weighted by how many pixels each has.
  • Auto levels stretches the histogram so the darkest 1% becomes black and the lightest 1% white; Equalize spreads brightness evenly over the whole range, which brings out very faint text (and noise).

The viewer then shows exactly the image the model receives, the same bytes at the same size, with its pixel size and file size (Hold to compare flips back to the original). Fewer pixels usually means fewer input tokens; grayscale mostly shrinks the upload, not the token count.

The steps always run in a fixed order, whatever order you set them in: rotate, crop, grayscale, denoise, levels, brightness, contrast, sharpness, black & white, invert. Geometry comes first, so crop edges refer to the page as you see it. Denoise runs before contrast, because contrast would amplify the specks. Thresholding runs near the end, because it throws away information every earlier step needs.

Is it better? The settings are part of the cache key, so "model X on the original page" and "model X on the cleaned page" are two separate sources. A/B: original vs adjusted in the LLM tab runs both and diffs them, next to their token counts and timings. A diff only shows what changed. To know which version is right, score each against text you trust: the native layer of a born-digital PDF, or a page you have checked by hand. For a whole document, put the same settings in Image preprocessing on the Overview page and use Compare. The settings are remembered per document and shown as a short spec (for example gray;auto;contrast=1.5) that pyocr extract --preprocess accepts too.

Comparing: CER and WER

To find out how wrong a text is, compare it with a text you trust more: the reference. The basic quantity is edit distance (Levenshtein distance): the smallest number of single-item insertions, deletions and substitutions needed to turn the candidate into the reference.

reference : the cat sat
candidate : the bat sat        → 1 substitution (c → b)

CER = character edits / reference characters = 1 / 11 = 9.1 %
WER = word edits / reference words           = 1 / 3  = 33 %
  • CER (character error rate) is the usual OCR quality figure. As a rough guide, under 2 % is excellent (green), 2–10 % is usable with care (amber), and over 10 % will hurt downstream extraction (red).
  • WER (word error rate) is harsher, because one wrong letter makes the whole word wrong. It is closer to what matters for search and for exact values such as invoice numbers or amounts.
  • Both can be over 100 % when the candidate contains a lot of extra text.
  • The whole-document CER on the Compare page is micro-averaged: total edits divided by total reference characters. Long pages count more than short ones, which matches how much text is actually affected.

Before scoring, whitespace is collapsed, because engines break lines differently and that is not a reading error. Ligatures such as ﬁ are normalised to fi, and words hyphenated across a line break are joined. Case and punctuation can optionally be ignored as well.

Disagreement is not the same as error. "OCR vs LLM" tells you how much two engines disagree, not which one is right. For real ground truth, use a born-digital PDF: its native text is exact, so comparing OCR and each LLM against it shows how every engine performs on your kind of documents.

Typical workflows

Is OCR good enough for this batch of scans?

  1. Upload a representative document.
  2. Extract with Tesseract and an LLM (verbatim) on all pages.
  3. Compare: reference = LLM, candidate = Tesseract OCR. Check the overall CER and the worst pages.
  4. Open the worst pages in the inspector and read the diff. Are the errors in places that matter, such as numbers and names?

Which LLM should our pipeline use?

  1. Take a born-digital PDF, which has exact native text.
  2. Run two or three models on the same pages.
  3. Compare native text (reference) against each model (candidate). Lower CER means a more faithful model. Also look at the cost on the Overview page: each job shows its spend at list price in US dollars and rupees (set USD_INR_RATE to today's rate).
  4. Compare model A against model B on your real scans to see where they disagree.

Just get clean text out of a hard PDF

  1. Extract with an LLM using the Markdown prompt.
  2. Open Full text, check it next to the page images, then download as Markdown or JSONL.

Export and GenAI pipelines

Every source can be downloaded for the whole document (Overview → Export, or the Download menu in Full text):

  • TXT: pages separated by ===== Page N =====.
  • Markdown: a ## Page N heading per page.
  • JSON: {document, source, pages: [{page, text, extracted}]}.
  • JSONL: one JSON object per page (document_id, filename, page, source, text), ready for chunking, embedding or loading into a vector store.

Pages that have not been extracted for that source are left empty. An export never starts a paid LLM call.

Search

Search is case-insensitive, and a phrase matches even when it is split across lines. In the page inspector, hits from the native text are drawn in yellow and OCR hits (any engine) in blue, using each word's coordinates. LLM output has no coordinates, so its hits appear as text snippets. OCR and LLM text is only searchable on pages where it has been extracted.

Setting up providers

Easiest: open Providers, expand Set up in the browser on a provider card, paste your key and click Save. It takes effect immediately, is stored only on this machine in DATA_DIR/credentials.json (readable only by you), overrides environment variables, and is never sent back to the browser. Tick forget saved value to fall back to the environment again.

Alternatively run pyocr init to create a .env file, fill in the keys you have, and restart pyocr serve. Either way, click Test connection to check.

You can type any model or deployment name in the model box. The suggestions are only hints. The model must accept images: for local models, use a vision model such as qwen2.5vl or llama3.2-vision.

The Models page is a searchable catalog of vision models rated for this job (Excellent, Good, Fair: clean print only, Not suitable), with prices and the reason for each rating, and links to the benchmarks used. List models asks a provider which models your key can use and rates each one. The same rating appears under every model box as you type; names that aren't in the catalog are marked custom and still work. Ratings are a starting point: measure on your own pages with Compare.

Command line

pyocr serve [--host 0.0.0.0] [--port 8000] [--open]   # start this web app
pyocr init                                            # write a .env template here
pyocr doctor                                          # check Tesseract, providers, data dir
pyocr providers                                       # list providers and their status
pyocr extract FILE --engine llm -p anthropic --pages 1-5 --format jsonl -o out.jsonl
pyocr extract FILE --engine ocr                       # Tesseract, all pages, text to stdout
pyocr extract FILE --engine ocr:paddleocr             # another OCR engine (`pyocr engines` lists them)
pyocr extract FILE --engine native --format md        # embedded text layer only
pyocr compare FILE -p openai -m gpt-6.2-sol                 # per-page OCR/native error rate vs an LLM
pyocr extract FILE --preprocess clean                 # adjust the image first (a preset or e.g. 'gray;auto;contrast=1.5')
pyocr import a.pdf b.pdf scans.zip folder/ -w "Q3"    # add many files as one workspace (zips unpacked)
pyocr import FILE... --no-workspace                   # add to the Library without grouping

Documents processed from the command line also appear in the Library, so you can inspect them in the browser afterwards.

Data and privacy

  • Everything is stored under DATA_DIR (default ./data): the original file, OCR results and LLM results as plain JSON. Workspaces are small JSON files in workspaces/ that list document ids.
  • A page image goes to an LLM provider only when you start a transcription for that page, and only to the provider you chose. The same goes for cloud OCR engines (Google Vision, Azure, Textract, Mistral). Native text, Tesseract and the local OCR engines never leave your machine.
  • API keys are read on the server and are never sent to the browser.
  • There is no login. Keep it on 127.0.0.1 (the default) or put it behind your own authentication before sharing it on a network.

Troubleshooting and FAQ

“Tesseract OCR is not available”
Install Tesseract (see Providers) and restart. For languages other than English, install the matching pack (for example tesseract-ocr-deu) and set TESSERACT_LANGUAGE.
A provider says “not configured”
The required environment variable is not visible to the server. Put it in .env in the directory where you run pyocr serve, or export it, then restart.
“authentication failed” / “model not found”
Check the key and the model name. For Azure, the model box needs your deployment name, not the model family.
“output hit the max token limit”
The page has a lot of text. The transcription is truncated; try the verbatim prompt, which is shorter than Markdown, or a model with a larger output limit.
The LLM “fixed” words that are misspelled on the page
That is a known LLM habit. The verbatim prompt discourages it, and the diff view makes it visible. If exact characters matter (IDs, legal text), compare against native text or OCR.
OCR is slow
Tesseract at 300 DPI takes roughly 1–5 s per page. Results are cached, so each page is only OCR'd once. Lowering OCR_DPI to 200 is faster and slightly less accurate.
Native text has words in the wrong order or odd characters
The PDF's internal structure or font mapping is unusual. This is exactly the kind of problem this tool is for: compare against OCR or an LLM to see the difference.
Can I use it with a local model and no internet?
Yes. Run Ollama with a vision model and set OPENAI_COMPATIBLE_BASE_URL=http://localhost:11434/v1.
